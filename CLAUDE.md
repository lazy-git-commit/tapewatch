## Architecture

**Full algorithm documentation lives in `docs/algorithm.md`** — every filter,
threshold, and the incident that motivated it. Keep it updated with any rule change.

The system runs four APScheduler background jobs from `main.py`:

**`news_cycle`** (every 1 minute, unconditional):
Session-gated (v21, `market/sessions.py::get_trading_session` — T212 24/5 sessions ET: premarket 04:00–09:30, regular 09:30–16:00, afterhours 16:00–20:00, overnight 20:00–04:00). **regular**: pre-market candidate evaluation (first 30 min) → retry queue → `news/fetcher.py` → `market/price_check.py` → risk gates → `trading/executor.py` (buy + **resting STOP** — v20) → `storage/database.py`. **afterhours** (`AFTERHOURS_TRADING_ENABLED`, **default OFF as of v21.6, 2026-07-27**): same pipeline in the extended regime — anchored session analysis, RVOL band replaced by `EXTENDED_MIN_SESSION_DOLLAR_VOLUME`, ADV$ ≥ `EXTENDED_MIN_ADV_DOLLAR` ($50M), spread ≤ `EXTENDED_MAX_SPREAD_PCT`, `EXTENDED_SIZE_FACTOR` (0.5) sizing, extendedHours market orders, **no resting stop** (T212 stops execute RTH-only; the monitor polls both sides). ⚠️ **Turned off, not just inert**: pre/post-market bars are a Twelvedata Pro/Venture entitlement — our plan 403s every `prepost=true` request, for every symbol — and Finnhub's free quote freezes at the 16:00 ET close, so no extended signal was ever confirmable (0 of 18 trades all-time carry a non-`regular` session). `twelvedata_bars` still latches the 403 on first sight (`extended_bars_available()`) as a defense-in-depth backstop, but the deploy workflow (`.github/workflows/deploy.yml`) now writes `AFTERHOURS_TRADING_ENABLED=false` directly, so entries are off by config, not by a runtime probe. `EXTENDED_HOURS_ENABLED` stays **true** — `is_manage_session` deliberately keeps managing/flattening any position that leaks into the session even with entries off (see its docstring in `market/sessions.py`). Flip `AFTERHOURS_TRADING_ENABLED` back to `true` in the workflow once the Twelvedata plan covers prepost data. **premarket**: scanner builds the at-open watchlist (08:00–09:30 window as before); direct entries only behind `PREMARKET_TRADING_ENABLED` (default off). **overnight/closed**: returns immediately — Blue Ocean (20:00–04:00) is invisible to Finnhub/Twelvedata, so the system is fail-closed there by construction. See docs/algorithm.md §12. Never reschedules its own trigger; rescheduling from within a running job causes APScheduler to silently drop the replacement.

**`monitor_positions`** (every `MONITOR_INTERVAL_SECONDS`, default 5s — v20; early-outs on a local DB query when flat):
**v21 session awareness**: positions are managed in regular hours AND (with `EXTENDED_HOURS_ENABLED`) premarket/afterhours — extended sells carry the `extendedHours` flag, go market-first (the API rejects the flag on limit orders; feature-detected per process via `executor._extended_limit_supported`), and verify their fill instead of assuming it. **After-hours flatten**: everything force-closed `EXTENDED_FLATTEN_BUFFER_MINUTES` (15) before 20:00 ET — past that the tape moves on Blue Ocean, which our data providers don't carry. The ratchet arms the polled breakeven only (no resting re-place) in extended sessions. Everything below is the regular-hours behavior, unchanged:
`monitor/position_monitor.py` manages exits under the **v20 inversion**: the STOP rests at the broker (`stop_order_id`, stop-market, placed at buy time — zero latency on the loss side; realized record: 1 resting-TP fill in 11 trades vs stop slippage −3.4/−3.97/−18.99% under the old polled stop), the monitor notices its fill (order-status + fill-detail check; GONE ≠ filled; status checks throttled to 15s/trade — v20.1) and POLLS take-profit (+5%) and time-stop (60 min), force-flattening everything `EOD_FLATTEN_MINUTES` (10) before the close. **Breakeven ratchet**: at +`RATCHET_TRIGGER_PCT` (2%) the stop is cancelled/re-placed at buy×(1+`RATCHET_LOCK_PCT`/100), once; the armed flag is **persisted on the trade row** (`ratchet_armed`, v20.1 — survives restarts) and set only after the move resolves, so a crash mid-move self-repairs by placing a fresh breakeven stop next cycle; placement failure falls back to a polled breakeven stop. **v21.5 settle period**: not eligible until `_RATCHET_MIN_AGE_SECONDS` (15s) after the fill — HOG (2026-07-23) filled 3.6% off its signal price on a thin book, and one second later the ratchet read that same noisy quote as +3.75%, cancelling the fresh −2% stop and racing its breakeven replacement into a broker 429 (4th T212 order call for the position within one second); the position then sat below its (never-placed) breakeven line for 32 minutes with no resting stop before exiting at the time-stop. The same incident exposed a logging gap — the polled holding-check only logged at DEBUG — now promoted to INFO once per `_PRICE_LOG_EVERY_SECONDS` (60s) per trade so the price the monitor is actually comparing against is provable from the logs. Before any polled sell it cancels the resting order and handles the cancel/fill race (both kinds). Polled sells are bounded LIMIT orders (`SELL_LIMIT_SLACK_PCT`) with market fallback; **v19.2 stuck-exit escalation** — after `_SELL_ESCALATE_AFTER` (3) consecutive unfilled limit attempts for one trade, the next attempt is a market order + one `exit_stuck` system_event. EOD flatten uses a market sell because avoiding overnight gap risk takes priority. Broker reconciliation throttled to 60s and runs BEFORE the flat-DB early-out (v21.2 — an orphan whose failed `open_trade()` left the DB empty must still be found); **v21.2 two-pass confirmation** — a divergence (orphan: broker-open/DB-flat, or phantom: DB-open/broker-flat) fires `CRITICAL` only after surviving two consecutive passes, first sighting is INFO — a mid-cycle fill whose DB commit is still in flight self-resolves by the next pass, while a real divergence can't clear itself (replaces the v21.1 time-based grace window, which also masked a genuinely failed `open_trade()` and ignored the phantom-side race). The monitor's `get_current_price` runs the quote chain fast (single-attempt) with the 390-bar fallback throttled to 30s/symbol (v20.1). Legacy pre-v20 trades with a resting TP (`tp_order_id`) keep the old handling until they close.

**`forward_returns`** (nightly 22:30 UTC): `analysis/forward_returns.py` fills 5/15/60/**120-min and EOD** forward returns for every Claude classification in `sentiment_scores` (yfinance — free, retrospective). This is the prompt-eval feedback loop. **v21.3: the 120m/EOD horizons** were added because the 60-min panel showed the tradeable-catalyst edge (guidance_raise +3.8%/60m, fda_approval +1.1%/60m) still *climbing* at 60 min — i.e. the 60-min time-stop was clipping it mid-move; these columns size the hold on a large sample. `update_forward_returns()` is COALESCE-guarded (a recompute that comes back NULL never clobbers a measured value); `reset_for_extended_returns()` re-opens the recent (in-yfinance-window) rows once to backfill the new horizons, self-limiting via the `_FWD_RETURN_120M_DEPLOYED` cutoff like the anchoring-fix repair. The maturity guard is 125 min (was 65) so the 120-min window is finished before a row is finalized.

**`symbol_map_rebuild`** (daily 08:00 UTC): refreshes the T212 symbol map.

Portfolio risk gates in `main.py` (checked before every entry, re-checked after every fill): daily kill switch (`MAX_DAILY_LOSS_PCT` realized → stand down until tomorrow, fail-closed), `MAX_OPEN_POSITIONS` (**v21.13: 3 → 8**, so concurrency stops capping the sample size while the strategy is being measured; bounded — 8 × ~5% = ~40% deployed and 8 simultaneous −2% stop-outs is ~0.8% of portfolio, inside the 2% kill switch. ⚠️ this gate has **never rejected a signal** — 0 hits since 2026-08-01 — so expect little change in trades/day: throughput is limited by the price gates, not concurrency), `MAX_TRADES_PER_DAY`, 24h per-ticker cooldown. **Entry slippage (v21.13, `main._record_entry_slippage`)**: every entry logs the signal→fill gap, and past `_ENTRY_SLIPPAGE_ALERT_PCT` (1.0%) raises a WARNING + one `entry_slippage_high` system_event per day. LAMR 2026-08-06 was sized at $161.09 and filled at $164.30 (+1.99%, after 34s vs 3–4s for the day's other entries) — above the stock's high for the entire session; the stop then sat 2% below a price we never chose and a drift back to the signal price stopped us out 28s after entry. ~£6 of that day's £17.96 loss was entry slippage. Note most fills sit 0.01–0.26% above the minute bar's high, which is ordinary bid-ask spread (bars record trades, a market buy pays the ask) and is NOT a fault — the alert threshold is set well clear of it. **Entry cutoff (v21.3, `price_check.is_too_late_to_buy`)**: no new position within `ENTRY_CUTOFF_MINUTES` of the session's hard exit boundary — **decoupled from the hold** (`TIME_STOP_MINUTES`) so lengthening the hold to capture the slow catalyst grind doesn't collapse the entry window. `ENTRY_CUTOFF_MINUTES` defaults to the time-stop value (behavior unchanged unless set explicitly). **Session no-quote blackout**: `_no_quote_blackout` (set) + `_no_quote_ticker_strikes` (dict) suppress tickers with no Finnhub/Twelvedata coverage after `_NO_QUOTE_BLACKOUT_RETRIES=2` failed retries — prevents perpetual retry loops that drain credits. **v21.6 scoping**: the blackout asserts "no provider carries this instrument", so only a miss in a session where data is genuinely expected may count — extended-session misses pass `count_strike=False` (our Twelvedata plan has no pre/post bars at all, so an after-hours miss proves nothing about the ticker), and `_reset_no_quote_blackout_if_new_day()` clears it on each new ET trading day. Both fixes come from 2026-07-27, when nine liquid large/mid caps (CDNS, SANM, CLS, KFRC, LOKB, TFII, SJW, SUI, LC) were permanently blacklisted purely for reporting earnings after the bell; the old "resets on service restart" was fiction on a systemd unit that had run six days with `NRestarts=0`. **v21.11 scoping part 2**: v21.6 exempted *extended* misses, but a REGULAR-session provider freeze is a session where data is genuinely expected, so strikes still counted — on 2026-07-31 GTES and IRMD were blacklisted and four of nine premarket candidates expired "no quote after 3 retries" while both feeds served the previous day's close for every symbol, SONY included. `price_check.quote_feed_degraded()` exposes the LIVE stale streak (not the once-per-process alert latch — reading that would suppress strikes all day after one outage) and both strike sites (`main._queue_retry`, the premarket evaluator) skip the strike while any feed is frozen. The system already *detected* the freeze at 09:31:56 via `stale_quote_feed`; the blacklist just wasn't listening. **v21.12 scoping part 3 — the detector itself**: a stale streak now also has to span `_STALE_QUOTE_MIN_DISTINCT_SYMBOLS` (3) DISTINCT symbols before `quote_feed_degraded()`/the alert call a provider frozen. On 2026-08-04 MZDAY (Mazda's OTC ADR, whose whole day ranged $3.38–$3.55) sat in the re-eval queue and was polled 221 times; ten in a row tripped the tripwire on BOTH providers (Twelvedata 09:33 ET, Finnhub 09:51) while the feeds were fine — BE was quoted correctly two minutes later and traded all session. That false alarm **closes a loop**: `quote_feed_degraded()` suppresses the strikes that would blacklist a dead ticker, so MZDAY protected itself from blacklisting and kept polling to re-trip the alarm, all day. The 2026-07-31 outage served the previous day's close for *every* symbol asked, so it clears a distinct-symbol bar trivially — the original protection is intact. `_note_quote_fresh()` clears the symbol set with the streak, so a feed alternating fresh/stale can't accumulate its way over the bar.
**Kill-switch / snapshot collision (v21.11)**: `get_portfolio_value()` is called by the kill switch only when `realized < 0`, and `portfolio_snapshot` runs every 5 min — APScheduler anchors both to process start and 5 is a multiple of 1, so they hit the rate-limited `/equity/account/cash` on the same instant every fifth minute forever. 2026-07-31: 64 rejections, **44 of which stood an entire news cycle down** (`kill-switch check impossible — standing down`), i.e. the system went ~20% blind for the rest of the day *because* it was already losing. Fixed in `executor._fetch_cash()` by a lock (the actual fix — it serializes the racers) + a 15s TTL cache (3s for order sizing) + one retry on a retryable status.

### Key data contracts

- `news/fetcher.py` fetches articles from Benzinga via massive.com and applies pre-filters before Claude: (1) freshness — older than `max_age_minutes` (3 min during RTH; the session-scoped `_scored_articles` set ensures Claude scores each article exactly once, so the window can exceed the poll cadence with no re-scoring cost — v18); (2) crypto tickers — `X:`-prefixed stripped; (3) roundup articles — >3 tickers skipped; (4) analyst-action headlines (`_ANALYST_ACTION_RE`); (5) **digest/preview headlines (`_DIGEST_RE`, v20)** — "Market-Moving News…"/"Stocks To Watch"/listicles never reach Claude (a 3-ticker digest fabricated "earnings_beat conf=0.8" for three unrelated companies and bought the top of CRCL's 13% spike, 2026-07-10); (6) **explainer/recap headlines (`_EXPLAINER_RE`, v21.12)** — "What's Driving…"/"Here's Why…"/"…Stock Charges Higher"/"…Shares Are Trading Higher"/"post-earnings rally" never reach Claude either. An article ABOUT a move that already happened is not the catalyst that caused it, and the primary newswire item arrives separately so nothing tradeable is lost. Trade #25 (BE, 2026-08-04, −2.82%, the only trade of the day) came from "Bloom Energy Stock Charges Higher Tuesday: What's Driving the Post-Earnings Rally?" — scored `guidance_raise`/positive/conf 0.75 with **`already_moved` = False**, while the headline says in its own words that the rally was underway and the stock was already +3.99% on the day at entry; `already_moved` is the one field that would have blocked it. Validated against 2,415 real scored headlines: 49 matches (2.0%), zero false positives, exactly one of the 49 had scored positive (that article). Same reasoning as `_DIGEST_RE` — a deterministic title check beats hoping the classifier reads through a template it has demonstrably misread. Remaining articles are scored by Claude Haiku in one batched call: `temperature=0`, rubric in a **cached system prompt**, **forced tool use** (schema-validated output). **v21.16 — that cache had never once engaged**: `cache_control` is a request HINT, and Haiku 4.5 will not cache a prefix below **4096 tokens**, silently ignoring the field (200 OK, zero cached tokens, no error). Across the first 1,140 Claude calls `tokens_cached` summed to **exactly 0**, while Qwen — whose OpenAI-compatible endpoint caches automatically with no minimum — accumulated 38,272. The cached prefix (tools + system) was ~3.5k tokens, ~600 short, so every call paid full input price for the rubric (3.18M full-price tokens in one week). Fixed by giving the rubric content it should have had anyway — **worked examples drawn from real misclassifications** (the BE post-earnings-rally explainer, the CRCL 3-ticker digest, acquirer-vs-target, offering dilution) plus a `guidance_raise` boundary section, which is the DEEPER fix for `_DIGEST_RE`/`_EXPLAINER_RE`: those patch two headline shapes, the examples teach the principle. Do NOT trim `_SYSTEM_PROMPT`/`_CLASSIFY_TOOL` below ~14.3k characters without re-checking `tokens_cached`. Two guards: `_note_cache_usage()` raises `claude_cache_ineffective` after 25 consecutive uncached calls (**warning, not critical, by design** — a cost regression is not a trading outage and must not page or dilute the critical set), and `tokens_cached` now counts cache **creation** as well as reads (Anthropic reports `input_tokens` as the non-cached remainder only, so counting reads alone made the first call of every 5-min TTL window — the write — look identical to no caching at all). **v21.7/v21.12: retries on an empty result** — a well-formed but empty `classifications` list for a non-empty batch is not a parsing failure (200 OK, forced tool use, no per-record validation warnings); `_mark_scored()` only fires on success, so an un-retried empty batch silently regrows the unscored backlog every cycle until it self-recovers or ages out via `max_age_minutes`. v21.7 added one retry; v21.12 raised it to 3 attempts plus a `claude_empty_batch` system_event. **v21.13 reversed the retry half and added a cooldown, because retries demonstrably do not fix this failure**: 2026-08-04 saw 25 consecutive all-empty cycles with 1 retry, and 2026-08-06 saw **58** with 3 attempts each — 98 minutes (07:00–08:38 ET), ~174 wasted API calls, nothing scored, and unlike 08-04 it overlapped the 08:00–09:30 ET premarket watchlist build by 38 minutes. `_EMPTY_BATCH_ATTEMPTS` is back to **2** (one retry, which only ever helps on a genuinely isolated blip), and after `_EMPTY_BATCH_COOLDOWN_TRIGGER` (2) consecutive all-empty CYCLES the classifier is stood down for `_EMPTY_BATCH_COOLDOWN_SECONDS` (120) via the same `_enter_claude_cooldown` used for 529/billing failures — the next two minutes then cost zero CLAUDE calls instead of ~6 (shadow mode still calls Qwen — see below, that is deliberate), articles stay eligible (`_mark_scored` only fires on success) and are re-offered when scoring resumes, and any successful cycle clears the streak (`_consecutive_empty_batches`). The `claude_empty_batch` event still fires, and it worked: the outage was visible in Grafana on both 08-05 and 08-06 instead of needing a journal grep. A missing `tool_use` block is a *parsing* failure and still returns immediately without burning the budget. **v21.15 — the empty-batch outages were OUR TRUNCATION, not Claude**: the output budget was `max(400, n*60+64)` from a comment claiming "~55 tokens/article", but the measured cost in `classifier_calls` is **68-72 tokens/article** — above the allowance, so large batches were cut off mid tool-call. A truncated forced-tool-use response still returns 200 OK with a `tool_use` block whose `input` never finished serialising, so `.get("classifications", [])` yields `[]` — identical to a genuine empty answer unless `stop_reason` is read. Proof (2026-08-12..14): 26 Claude calls had `tokens_out` EXACTLY equal to the cap, all 26 recorded `scored_count=0`, and there were exactly 26 `empty_batch` errors — 1:1. This explains every property the old theory couldn't: retries never worked (deterministic — same batch, same truncation), it self-reinforced (`_mark_scored` fires only on success, so the next batch is BIGGER), it always self-healed unaided (articles aged out, shrinking the batch), and it clustered at premarket/session boundaries (largest backlogs). `_TOKENS_PER_ARTICLE`=150 / `_MIN_OUTPUT_TOKENS`=1024 (~2x measured need — `max_tokens` is a ceiling, not a charge, and a schema-forced tool call cannot ramble to fill it), `stop_reason == "max_tokens"` is now detected and recorded as `truncated` + a `claude_truncated_batch` event, returning immediately WITHOUT consuming a retry or tripping the 120s cooldown — a config bug must not stand the classifier down. **v21.15.1 — raising the multiplier rescaled the cliff; capping the batch removes it.** Nothing bounded `len(articles)` (`to_score` is the whole unscored backlog, and a failed cycle GROWS it), so `max_tokens` was still a function of news volume. `_batch_score_sentiment` now chunks to **`_MAX_ARTICLES_PER_BATCH` (25)** — the same thing `backtest/backtest.py` has done for years — making the budget a bounded constant (4,006 vs ~1,800 measured need) and limiting any single failure to one chunk. Every property of the outage (deterministic recurrence, self-reinforcement, session-boundary clustering) was a consequence of unbounded n, not of the constant 60. The budget lives in one shared `_output_budget()` function called by the live path, the shadow, and the tests — v21.14.1 duplicated the formula and the copies drifted; v21.15 shared only the constants, which would have let a changed overhead term diverge silently again. Also v21.15.1: `claude_truncated_batch` is registered **critical** (the documented Grafana alert queries `severity='critical'`, so it was raising no alert at all), `_record_claude_event` is `live`-guarded like its sibling (a replay would otherwise consume the day's only alert slot via the `(event_type, event_day)` unique index and suppress the real one), and `truncated`/`bad_shape`/`client_unavailable`/`dropped_backlog` are excluded from liveness in `classifier_compare` — charging our own config bugs to a provider's reliability record is the exact accounting error v21.14.1 removed on the Qwen side. **v21.14 shadow mode (`news/shadow_classifier.py`)**: every batch the news path assembles is sent to **Qwen-Flash** (Alibaba Model Studio, OpenAI-compatible endpoint) — **Claude's verdict remains the only one that reaches a trading decision**; nothing is read back. Exists because Claude is the sole external dependency with no fallback and has now gone dark twice in three sessions. Four safety properties, all deliberate: (1) runs on a **background thread** so the news cycle never waits on it; (2) **single worker + bounded queue** (`_MAX_PENDING=2`) — a backed-up provider gets its batches DROPPED, never queued, since an unbounded queue turns a slowdown into a memory leak. **v21.14.1: each drop is still RECORDED** (`error_type='dropped_backlog'`, buffered in memory and written by the next background job so the news-cycle thread never touches the DB) — "the gap in the data is itself the signal" was wrong as implemented, because liveness is computed over the rows that EXIST, so a provider saturating the worker for an hour reported a high success rate and a zero failure streak; (3) every exception caught and recorded — a shadow failure is data, not an incident; (4) inert unless `QWEN_API_KEY`+`QWEN_BASE_URL` are set, and `cfg.validate()` deliberately does NOT require them so a missing secret can never crash-loop startup. Records are validated exactly as the live path does — out-of-range values **rejected, never clamped**. **v21.14.1 corrections (review pass)**: the shadow is dispatched BEFORE the Claude cooldown check — a cooldown means Claude is failing, which is the exact scenario a fallback is being evaluated for, so gating the shadow behind it would have guaranteed zero data about the one question that matters (cost is bounded and accepted: the same gate covers the 1800s billing cooldown, so a billing outage now costs ~30 paid Qwen batches). Claude now writes a `classifier_calls` row on EVERY failure path too — cooldown-suppressed cycles and all five exception handlers — because it previously recorded only calls that succeeded and parsed, so a total Claude outage rendered as success_rate=100%/streak=0 and the fallback decision would have been made on a dataset with Claude's outages deleted. Shadow validation now matches `fetcher.py` coercion-for-coercion (lowercased sentiment, defaulted confidence, `int()`-ed magnitude); divergence dropped Qwen rows from the INNER JOIN and removed its WORST answers from the paired sample, flattering the challenger by survivorship. The shadow request carries the same `max_tokens` budget as the live call — without it a truncated completion was recorded as Qwen's own `bad_json`, blaming the provider for our missing parameter on exactly the busiest cycles. `_batch_score_sentiment(live=False)` keeps backtest replays out of both production tables (`qwen_scores` is UNIQUE per article with ON CONFLICT DO NOTHING, so a replayed row would permanently block the real one). Assess with `python -m analysis.classifier_compare [--days N]` (read-only; latency as p50/p95 not mean, liveness as success rate AND longest consecutive failure streak, prediction judged on each model's own tradeable set's forward returns rather than agreement — and it refuses to imply a verdict below 200 calls/provider and 300 paired articles). Each article gets `sentiment`, `confidence`, `catalyst_type` (14-class taxonomy — **v20.2: `fda_approval` requires the US FDA specifically**, a non-US regulator such as Health Canada/EMA/MHRA is `other`, so a foreign approval can't dilute the measured FDA edge), `already_moved`. **Every score is persisted to `sentiment_scores`** (eval loop). Positives must then pass code gates to trade: confidence ≥ `MIN_SENTIMENT_CONFIDENCE`, catalyst in `TRADEABLE_CATALYSTS` (**v21.16 default: `guidance_raise` ONLY**; v20 had pruned to fda_approval+guidance_raise on raw forward returns — contract_win/earnings_beat/product_launch/ma_target measured negative. **v21.16 dropped fda_approval too**: raw forward return asks “does the stock drift up?”, not “does a trade with our stop survive to collect it?”. Simulated with the live exit rules (entry at signal, −2% stop, +5% TP, 120-min hold, 0.46pp costs): guidance_raise n=193 net **+0.667%/trade**, 50% win, t=5.51; fda_approval n=106 net **−0.146%**, 32% win, t=1.44 — below the 33% break-even the FX round trip imposes. t=1.44 is “no measurable edge”, not “proven to lose”, so this is capital allocation: at ~0.5 trades/day, splitting throughput with a zero-edge class halves the sample on the one that pays. Live P&L can’t arbitrate — fda_approval has ONE closed trade. Still scored, still accruing forward returns, re-enable on evidence. See docs/algorithm.md §3.3), `already_moved == False`, magnitude ≥ `MIN_CATALYST_MAGNITUDE`. Produces `NewsItem` dataclasses. **v19.5 same-day cross-reference**: a session-scoped `_ticker_history` dict records every scored article per ticker; the next article for that ticker carries prior same-day verdicts as a `PRIOR ARTICLE(S) TODAY` line in the user message, and the system prompt instructs extra skepticism toward a positive respin of a story that already had a negative reaction that session.
- `market/price_check.py` confirms a signal using a **quote with fallback** (Finnhub `/quote` → Twelvedata `/quote` when Finnhub has no coverage; both yield current price, open, **previous close** `pc`) plus **one Twelvedata session pull + cached daily stats (v20)**. Momentum baseline selected **by timestamp among TODAY's bars only** (`MOMENTUM_LOOKBACK_MINUTES`, staleness guard >10 min; v20 fixed the overnight-gap-as-momentum edge at the open). ### Configuration

All settings live in `config/settings.py` as a `Settings` dataclass, loaded from `.env` via `python-dotenv`. Import anywhere as:
```python
from config.settings import cfg
```
`cfg.validate()` raises `EnvironmentError` on startup if any API key is missing.

### Ticker detection and blocklist

There is no watchlist — the system relies on Benzinga tagging articles with stock tickers directly. `BLOCKLIST` in `.env` is a comma-separated list of Trading 212 instrument codes (e.g. `TSLA_US_EQ`) to permanently exclude.

### Demo vs live mode

`TRADING_MODE=demo` (default) sends orders to Trading 212's demo API. `TRADING_MODE=live` executes real trades against your Trading 212 ISA. The `cfg.is_live` property gates this in `trading/executor.py`.

### Logging

Logs go to stdout (captured by systemd journald on the VM). Each module uses `logging.getLogger(__name__)`.

### Deployment

Always deploy via `git push origin main`. GitHub Actions picks it up, rsyncs to the VM, and restarts the systemd service. **Never SSH and run commands directly** — changes would be overwritten on the next deploy.
